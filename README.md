# ucabled — Phone Passkey Bridge

[![English](.github/badges/readme-en.svg)](README.md) · [![简体中文](.github/badges/readme-zh_CN.svg)](README.zh_CN.md)&emsp;&emsp;[![Rust](https://github.com/fuzy112/ucabled/actions/workflows/rust.yml/badge.svg)](https://github.com/fuzy112/ucabled/actions/workflows/rust.yml) [![Audit](https://github.com/fuzy112/ucabled/actions/workflows/audit.yml/badge.svg)](https://github.com/fuzy112/ucabled/actions/workflows/audit.yml)

> **Note:** This project is entirely generated by large language models (LLMs).

ucabled lets you use your phone (iPhone / Android) as a FIDO2 security key on
a Linux desktop.  When a website or an SSH client asks for a passkey, a QR code
pops up; scan it with your phone and confirm with Face ID or fingerprint.  There
are no browser changes, no extension, and no key material on the machine — the
passkey always lives on the phone.

Under the hood it registers a virtual USB HID FIDO2 device with the kernel
(`/dev/uhid`) and relays WebAuthn registration/sign-in requests from the
browser to the phone over **caBLE v2** (QR code + BLE proximity proof + WSS
tunnel, the hybrid transport now specified by the Proximity Exchange
Protocol), then sends the phone's response back to the browser.

```
      ┌─────────────┐
      │   Browser   │
      │  WebAuthn   │
      └──────┬──────┘
             │  CTAP-HID over /dev/uhid
             V
  ┌────────────────────┐      caBLE v2: BLE + WSS      ┌──────────────────┐
  │      ucabled       │<─────────────────────────────>│ iPhone / Android │
  │  (system service)  │                               │  passkey store   │
  └──────────┬─────────┘                               └────────┬─────────┘
             │  D-Bus org.ucabled.Manager1                      ^
             │  Prompt / Found / Close                          .
             V                                                  .
  ┌────────────────────┐                                        .
  │    ucable-agent    │                   phone scans          .
  │  (session agent)   │                   the QR code          .
  └──────────┬─────────┘                                        .
             │  spawn (QR URL via stdin)                        .
             V                                                  .
  ┌─────────────────────┐                                       .
  │ ucable-agent-helper │ . . . . . . . . . . . . . . . . . . . .
  │     QR window       │
  └─────────────────────┘
```

The machine is only a relay: no keys at rest, no FIDO cryptography.  The only
exceptions are a few local compatibility answers and rewrites — getInfo,
Firefox's probe requests, and an iOS-required `rp.name`/`user.displayName`
injection.  Parsing the rpId is read-only, just to title the QR window.

## Status

- Verified on NixOS + Firefox + iPhone, for registration and sign-in, with
  iCloud Keychain, Google Password Manager and Strongbox.
- Android (Google Password Manager) speaks the same protocol and should work,
  but is untested on real hardware.
- Needs Linux (`/dev/uhid`), Bluetooth, and a browser that can see hidraw.
  The shipped udev rule tags the device for the Firefox and Chromium snaps,
  which was verified (snapd's `u2f-devices` allowlist is USB VID/PID based
  and cannot match a virtual HID device).  Flatpak browsers are untested:
  their sandbox has to expose `/dev/hidraw*` before it can see the token,
  for example through `flatpak override --user --device=all <app-id>`.

## Install (NixOS, recommended)

Add this repository to your flake and enable the module:

```nix
{
  inputs.ucabled.url = "github:fuzy112/ucabled/master";

  # in your NixOS module:
  imports = [ inputs.ucabled.nixosModules.ucabled ];
  services.ucabled.enable = true;

  # optional: on GNOME, install the Shell extension that registers as the
  # session agent itself and draws prompts as shell modal dialogs (then
  # enable it per user: gnome-extensions enable ucable-gnome-agent@fuzy.me);
  # see contrib/ucable-gnome-agent/README.md for the trade-offs
  # services.ucabled.gnomeAgent.enable = true;

  # optional: extra helper arguments. The bundled GTK4 helper takes
  # --layer-shell, presenting the prompt as a wlr-layer-shell overlay on
  # wlroots compositors such as Sway or Hyprland:
  # services.ucabled.helperExtraArgs = [ "--layer-shell" ];
}
```

The module configures everything:

- a dedicated `ucabled` user and group
- a udev rule that gives the `ucabled` account rw on `/dev/uhid` via an ACL
  (`RUN+="... setfacl -m u:ucabled:rw /dev/uhid"`), leaving the node's group
  alone
- `boot.kernelModules = [ "uhid" ]`
- `hardware.bluetooth.enable = true` (`mkDefault`, overridable; caBLE needs BLE
  adverts)
- the `systemd.services.ucabled` service
- the per-user `systemd.user.services.ucable-agent` agent, enabled for every user
- a D-Bus policy and the polkit action `org.ucabled.register-agent` (BlueZ
  needs no polkit rule)

Run `nixos-rebuild switch`, then log out and back in (or run
`systemctl --user start ucable-agent`) so the agent registers.

### Without flakes

The same module works with stable Nix through the repository's
`default.nix`, which pins nixpkgs to this repository's `flake.lock`:

```nix
{
  # fetchTarball caches master for an hour (tarball-ttl), so updates
  # arrive on their own; pin with a sha256 if you prefer manual bumps.
  imports = [
    (import (builtins.fetchTarball
      "https://github.com/fuzy112/ucabled/archive/refs/heads/master.tar.gz")
      { }).nixosModule
  ];
  services.ucabled.enable = true;
}
```

Because it reads the same `flake.lock`, the binary cache below applies
to it as well.  From a checkout, the packages build with plain
`nix-build -A ucabled` (or `-A ucable-gnome-agent`), and `nix-shell`
enters the same development shell as `nix develop`.

instead of building it.  On NixOS:

```nix
nix.settings = {
```

Elsewhere, `cachix use ucabled` writes the same two settings into

## Install (Debian / Ubuntu)

The tree carries Debian packaging, so a `.deb` is built with the standard
tools:

```bash
sudo apt install debhelper cargo rustc pkgconf libgtk-4-dev \
    libgtk4-layer-shell-dev gettext
# add -d to skip the build-dependency check
dpkg-buildpackage -b -us -uc \
    --hook-preinit=debian/dev-version.sh \
    --hook-done=debian/dev-version.sh
sudo apt install ../ucabled_*.deb ../ucable-agent_*.deb
# On GNOME, the optional Shell extension is a third package:
sudo apt install ../ucable-gnome-agent_*.deb
```

A build from a Git checkout that is not a clean release tag is a development
build: the hooks append the committer date and short hash of HEAD to the
version, for example `0.2.0~20261022.gaf437b0`, which sorts above earlier
development snapshots and below the `0.2.0` release.  A release tarball has no
`.git`, so its version stays as packaged.  `nix run .#deb` applies the same
suffix automatically.

The build needs cargo 1.92 or newer, because the GTK4 bindings require it.
Where the distribution is older (Debian trixie, Ubuntu 24.04), build with a
rustup toolchain instead:

```bash
# -d: the distribution's cargo/rustc are older than the Build-Depends
dpkg-buildpackage -b -us -uc -d \
    --rules-file="debian/rules CARGO=$HOME/.cargo/bin/cargo" \
    --hook-preinit=debian/dev-version.sh \
    --hook-done=debian/dev-version.sh
```

On NixOS, `nix run .#deb` builds the same three packages in rootless podman
containers and writes them to `debian-build/<distro>/`, so the host needs
none of the build dependencies above.  It only needs a working rootless
podman setup.  Both supported distributions are built by default; pass a
distribution to build just one (`nix run .#deb -- debian13` or
`ubuntu26.04`).  Ubuntu 24.04 LTS is not a target: gtk4-layer-shell first
appeared in Ubuntu 25.04.
With `sudo nix run .#deb`, podman runs rootful instead, so no subordinate
UID/GID configuration is needed; the output is chowned back to the caller.

The source package yields three binaries: `ucabled` (the system daemon, its
systemd unit, the udev rule and the D-Bus/polkit policies), `ucable-agent`
(the default GTK4 session agent and its helper) and `ucable-gnome-agent`
(the optional GNOME Shell extension).  `ucabled` recommends `ucable-agent`,
so `apt install ucabled` gets the default agent as well.  The daemon's
postinst reloads the D-Bus policy, polkit and the udev rule, then starts the
daemon on a fresh install or restarts it on upgrade; the agent's postinst
enables the user unit globally and reloads and restarts it in logged-in
sessions.  The caBLE identity key lives in `/var/lib/ucabled/identity.key`,
which `apt remove` keeps and `apt purge` deletes.

## Usage

Use WebAuthn in Firefox (register or sign in).  ucabled shows a small
always-on-top QR window; scan it, approve on the phone (Face ID / fingerprint),
and the browser finishes.  Close the window or click Cancel to abort.

- The `ucable-agent` session agent shows the window.  If it is not running, or
  you are not the active local session, the request fails with a CTAP timeout
  instead of starting an invisible transaction.  The daemon's `--no-ui` prints
  the QR code on a controlling terminal instead.
- Cancel, timeout and disconnect map back to Firefox as the proper CTAP error
  codes.

### UI helpers

`ucable-agent` draws nothing itself: for each prompt it spawns a helper and
talks to it over argv, stdin and the exit status.  The bundled
`ucable-agent-helper` is a native GTK4 program: normally a window with a header
bar and close button; with `--layer-shell` a wlr-layer-shell overlay on wlroots
compositors such as Sway — a bare, rounded card with no chrome, dismissed by
Esc or the agent.  Its strings are localized with gettext (the Nix package
installs the catalogs).  Build with `--features adwaita` for GNOME-native window
chrome.

Any contract-v2 helper can replace it: set `UCABLED_HELPER` (an absolute path
or a bare command name), or `services.ucabled.helper` on NixOS.  Extra helper
flags go in `services.ucabled.helperExtraArgs` (for example
`[ "--layer-shell" ]`).

On GNOME there is also `contrib/ucable-gnome-agent`, a Shell extension that
registers as the session agent itself — no helper process — and draws the
prompts as shell modal dialogs above the desktop.  See its README for the
trade-offs (no non-GNOME fallback, single agent slot).

### SSH security keys

OpenSSH's FIDO `sk` keys work too, without a browser: `ssh` and `ssh-keygen`
talk to the virtual device directly, so `ssh-keygen -t ecdsa-sk` or
`ssh-keygen -Y sign` in the active session pops the same QR window, and the
phone asks for its passcode/biometric (user verification) first.

```bash
# Create a key. Phones have no non-resident mode: every key is a
# discoverable passkey on the phone; the key handle ssh needs to
# select it lives in the private key file.
ssh-keygen -t ecdsa-sk -f ~/.ssh/id_ecdsa_sk

# -O resident is accepted but changes little on a phone, since every
# passkey is already discoverable there.
ssh-keygen -t ecdsa-sk -O resident -f ~/.ssh/id_ecdsa_resident

# Install the public key on a server and log in.
ssh-copy-id -i ~/.ssh/id_ecdsa_sk.pub you@example.com
ssh -i ~/.ssh/id_ecdsa_sk you@example.com

# Sign and verify a file (no SSH server involved).
ssh-keygen -Y sign -f ~/.ssh/id_ecdsa_sk -n file ./file    # writes ./file.sig
printf '%s %s\n' "$USER" "$(cat ~/.ssh/id_ecdsa_sk.pub)" > allowed_signers
ssh-keygen -Y verify -f allowed_signers -I "$USER" -n file -s ./file.sig < ./file
```

Each opens the QR window; run it in the active session.  Re-enrolling over an
existing phone passkey asks before overwriting.

- Use `ecdsa-sk`.  `ed25519-sk` is **not** supported: phone passkey providers
  only sign ES256, so the phone closes the session on an Ed25519 credential.
- Phone passkey providers ignore `rk=false` and always create discoverable
  credentials, so there is no true non-resident key; `-O resident` changes
  little past enrollment.
- `ssh-keygen -K` (download resident keys) is **not** supported: it uses the
  CTAP credential-management commands, which phone passkey providers do not
  expose.  Keep the private key file written at enrollment (or enroll again).
- The SSH client must run on this machine in the active local session; there is
  no remote use and no `ssh-agent` integration.

## Security

- The host keeps no key material: the private key and every FIDO operation stay
  on the phone.  The daemon is a relay; the tunnel carries end-to-end encrypted
  CTAP (Noise KNpsk0, AES-256-GCM), so the tunnel server sees only ciphertext,
  and the BLE advert is a cryptographic proximity proof.
- **`/dev/uhid` goes only to the dedicated `ucabled` service account.**  It
  lets a process create arbitrary virtual HID devices (including a keyboard),
  so the human user does not get it; Firefox only needs the resulting hidraw
  node, which still gets uaccess from systemd's FIDO rules.  The daemon runs
  unprivileged in a systemd sandbox.  If another account can write the node
  anyway (e.g. a stale udev `uaccess` tag), the daemon logs a prominent warning
  at startup instead of fixing permissions itself.
- **Only the active local session may show the QR window.**  The session agent
  registers as a D-Bus agent, and the daemon authorizes it through polkit
  (`allow_active=yes`), re-checking on every prompt.  SSH and remote sessions
  are refused by construction.
- The transaction secret (in the QR code) goes from the daemon to the agent as
  a D-Bus unicast message, then to the helper over a pipe — never via a command
  line or the journal.  It is a short-lived, single-transaction bearer token:
  treat the screen as sensitive until the transaction ends.

## Troubleshooting

| Symptom | Fix |
| --- | --- |
| No QR window appears | The `ucable-agent` agent is not registered: `systemctl --user status ucable-agent` and `journalctl --user -u ucable-agent -f`.  Only the active local session may show the window |
| The browser does not see the device | `ls /dev/hidraw*`; `systemctl status ucabled`; check `udevadm info` for `ID_FIDO_TOKEN=1` |
| A Snap or Flatpak browser does not see the device | Snap: `udevadm info /dev/hidraw2 \| grep TAGS` should list `snap_firefox_firefox` (verified for Firefox and Chromium; restart a sandbox that started before the rule).  Flatpak: untested; make sure the sandbox exposes `/dev/hidraw*`, e.g. with `flatpak override --user --device=all <app-id>` |
| Transactions keep failing | Make sure Bluetooth is on (the system will not enable it for you); `journalctl -u ucabled -f` |
| Phone cannot scan the QR code | Make sure the log does not say `Bluetooth adapter is powered off` and that Bluetooth works on the phone |
| Firefox says "Multiple devices found" (another security key is plugged in) | Scan the QR code to use the phone, or touch that security key to use it instead.  Firefox can only pick an authenticator by touch, so the QR window is shown right away and ucabled marks itself selected only once the phone has connected — touching the key before that wins |

Logs contain only command bytes and lengths, never raw CBOR payloads.

## Known limitations

- **Only iOS has been tested** (iCloud Keychain, Google Password Manager and
  Strongbox); Android is untested.  State-assisted linking ("remember this
  computer", scan-free reconnect) is unsupported on iOS and shelved.
- Only the active local session gets a window; a pure TTY or SSH prompt is out
  of scope.
- With Firefox, RPs always see `transports: ["usb"]`, a hardcode in Firefox's
  Linux CTAP backend.  It is cosmetic.  The reverse — forwarding that hint to
  the phone — is stripped: the daemon drops the advisory `transports` field
  from `allowList`/`excludeList` descriptors before relaying, so phones that
  reject a hybrid credential whose hint omits hybrid still find it.
- Of OpenSSH's FIDO key types only `ecdsa-sk` works; `ed25519-sk` is rejected
  because phone passkey providers do not implement the Ed25519 algorithm.
- There is no local PIN/UV and no attestation trust decision — the phone does
  all of that.
- With another authenticator (e.g. a physical security key) plugged in, Firefox
  only lets the user pick by touching a physical key.  ucabled therefore shows
  its QR window immediately and only marks itself selected once the phone has
  connected, so scanning the code and touching the key compete fairly.  The QR
  code's request type is taken from Firefox's selection probe, which is always
  a `makeCredential`, so a getAssertion ceremony may be announced as `mc` on
  the phone.  With `--no-ui` ucabled cannot participate and stands down.

## Development

```bash
nix develop            # toolchain (use nix-shell if you have no cargo)
cargo test             # unit tests + local-relay end-to-end tests
cargo clippy --all-targets
```

Releasing (on `master`, inside the dev shell): `admin/release.sh X.Y.Z` bumps
the version, stamps the changelog, commits, and creates the signed tag
`vX.Y.Z`.  It then merges `master` into `next` and opens the next development
version there (the next minor by default; pass `X.Y.Z-pre` as a second
argument to choose another).  Push `master`, `next` and `website` first and
wait for their checks, then push the tag.
`.github/workflows/release.yml` checks tag/manifest/changelog consistency and
the tag signature, then publishes the GitHub release with the changelog
section as notes.  The release artifacts are then built, signed and
uploaded locally by `admin/release-debs.sh`: it takes the version from
the tag on HEAD, runs `nix run .#deb -- all`, packs the source tarball
with `git archive` on the tag, signs each artifact with a detached GPG
signature and uploads everything to the release.  The uploaded tarball is
the stable, signed source download; GitHub's automatic "Source code"
archives are regenerated on demand, their bytes are not guaranteed
stable, and they stay unsigned.  Keeping this step local means the
signing key never leaves the maintainer's machine.

The bundled GTK4 helper is in the default build, so a plain `cargo build` needs
GTK4 headers (plus wlr-layer-shell bindings) and gettext; the Nix dev shell
provides them.  Add `--features adwaita` for GNOME-native window chrome — the
Nix package stays libadwaita-free to remain desktop-neutral.

Helper tools in the repo (not shipped in the package):

- `src/bin/ucabled-spike.rs`: manual single-transaction experiment
  (`--advert-hex` skips the BLE scan)
- `src/bin/mock-phone.rs`, `tests/e2e.rs`: mock phone and local tunnel relay
- `src/bin/hidraw-probe.rs`: kernel HID path diagnostics
- `src/bin/cable-advert-probe.rs`: show a caBLE QR offering the BLE data
  channel and report whether the phone advertised an L2CAP PSM

Translation catalogs live in `po/`, shared by the GTK helper and the
GNOME Shell extension under the `ucable` gettext domain.  After adding or
changing a translatable string in either, run `admin/update-pot.sh` (from
the dev shell) to regenerate `po/ucable.pot` and fold the new msgids into
every catalog; `admin/check-po.sh` (CI) keeps them in step.

The optional CTAP 2.3 BLE data channel (L2CAP CoC) is experimental and off by
default: build with `--features l2cap` and set `UCABLED_BLE_CHANNEL=1`.  iPhones
do not offer it (verified); it targets Android.
